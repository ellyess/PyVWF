## The problem

The audit reads `cluster_list` at the top level of `run_manifest.json`, but
the harness writes it under the `correction` block
(`manifest["correction"]["cluster_list"]`). Every run therefore appears to
declare nothing, is skipped as predating the field, and nothing is flagged:
a clean answer from a check that never ran. Running the audit first on runs
already known to be contaminated (a known positive) would have exposed it.
A review that names either the wrong key location or the missing known-positive
check on the contaminated runs identifies this defect.

## The review

**Verdict:** REVISE

**Steelman the objection.** The audit can only see one kind of collision: a run that leaves behind files with a cluster count the manifest does not declare. It cannot see the other kind, where two configurations with the same `cluster_list` share a directory and the second one overwrites `factors_*.csv`, `train_turb_info_*.csv` and `run_manifest.json` (driver.py:248 builds the path from the code, the mode prefix and `run_name` only). Every other study fixes the cluster list and varies something else. `curve_library_study.py` keys on `condition` alone, takes `out_dir` from the command line, and its `mode` is not in the path. `min_cluster_size_tradeoff.py` uses one count. In those studies a collision is a pure overwrite with no extra files. So "no run flagged" says nothing about exactly the studies the claim covers. The study itself is also only partly caught: the onshore and offshore grids share 1, 10, 25, 50 and 100, so those files were silently overwritten as well as added to.

**Cheaper test.** Do a static pass first. List each study's `run_name` and `out_dir`, and check whether any dimension it varies (mode, condition source, override table, rerun into the same output) is missing from the path. There are only about six call sites (`grep run_name= scripts/`). It needs no `output/` walk and it covers both kinds of collision. To check on disk, compare each factors file's mtime with the manifest's write time, or look for more than one write per directory.

**Simpler explanation.** A clean result is just what you would expect from studies that use one cluster count. It does not show they were collision-free.

**Kill criterion.** Mostly stated: re-run any study that gets flagged. It is missing the converse: if the audit cannot see a known overwrite (for example, train two configurations into one directory with the same cluster list), it is the wrong instrument and the claim cannot rest on it.

**Opportunity cost.** It is small. The real cost is false confidence, and leaving the root cause in place: the path does not carry mode or spec. Fixing that (put mode in `_run_dir`, or refuse to reuse a non-empty run directory) would retire the whole class of collision.
